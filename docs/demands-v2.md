## V2-P0 — [严重] 同一记录重复点击会产生重复 PR(状态:已记录,待修复)

### 现象

同一行点击两次「提交」,会生成两份独立 PR(同内容、两个分支),而期望始终只有一份在途提交。

### 复现路径

1. 行处于任意非终态,点击提交 → worker 处理完成,行进入 `审核中`,PR #1 打开;
2. 再对该行点击一次「提交」;
3. 下一轮轮询把该行视为**新一轮提交** → 新提交 ID → 新 branch → 新 PR #2(此时 PR #1 可能仍未合并)。

补充:快速双击(两次点击落在同一个轮询周期内)只置一次 `已请求=true`,是安全的;间隔超过一个处理周期的第二次点击必然触发。最终形态待修复时实测确认。

### 根因(代码阅读结论,修复时需验证)

现行规则:行状态为 `审核中/已通过/已拒绝` 时再次点击 = 开启新一轮提交(阶段 1 经确认后实施,但真实使用中把「重复点击」误判为「有意再提交」)。

相关锚点(修复时全部要动):

| 位置 | 内容 |
|---|---|
| [domain/status.py](../src/preset_sync_worker/domain/status.py) | `TERMINAL_STATES` 把 `审核中` 归为已收尾;`RETRYABLE_FOR_SAME_SUBMISSION` 不含 REVIEWING |
| [domain/submission.py](../src/preset_sync_worker/domain/submission.py) | `resolve_submission_id`:终态 → 直接生成新 ID |
| [services/submission_service.py](../src/preset_sync_worker/services/submission_service.py) | `process_record` 按快照状态调用上述解析 |
| [README.md](../README.md) | 「重复点击语义」段落:审核中/已通过/已拒绝 = 新一轮提交 |
| [test_service.py](../tests/test_service.py) | `test_terminal_state_click_opens_new_submission` **固化了当前行为**,语义变更时须连带改写 |

### 期望行为(细项待确认,见开放问题)

- 行处于 `审核中` 且该提交 PR 仍打开时,再次点击**不得产生第二份 PR**;
- 行处于 `已通过`(PR 已合并)/`已拒绝` 后再点击:是否允许新一轮(内容迭代),待用户确认;
- 内容与仓库现状完全一致的「新轮」提交,现状已有保护(与默认分支一致时抛永久错误、不建空 PR),应保持。

### 验收标准(草案)

1. `审核中` + PR 打开时重复点击 → PR 数量不增加,行保持 `审核中`(方案见开放问题 Q1);
2. 快速双击(同一轮询周期)→ 只产生一个 PR(现状已满足,补回归测试锁定);
3. 语义相关测试更新后,全部测试通过;阶段 1 其余行为(幂等重试、失败路径等)不回归;
4. README「重复点击语义」与状态机图同步更新。

### 修复方向提示(待定,供实施时参考)

- 方案 A:行处于 `审核中` 时忽略重复触发(已请求=true 但状态为审核中 → 不处理/提示);
- 方案 B:复用语义——`审核中` 重复点击视同对同一提交的重试(与 `处理中` 一致),收敛到既有 PR,不新建;
- 方案 C:内容有变化才开新一轮(需 diff 能力,成本最高,不优先);
- 另可在 Automation / 按钮侧限制重复触发,但 worker 端防御优先,不依赖改表格。

## V2-P1 — 「状态」列类型应固定为单选,worker 启动时校验类型(状态:已记录,待实现)

### 现状与问题

- 建表指南([README](../README.md))与 [fields.py](../src/preset_sync_worker/fields.py) 注释都要求「状态」为人工创建的单选列,但 `ensure_schema`([bitable.py](../src/preset_sync_worker/adapters/bitable.py) 第 269 行起)**只校验列存在性,不校验列类型**;
- 「状态」被误建为文本/多选列时,worker 照常启动、写入照常成功,但取值不构成选项,下拉筛选、按选项语义的自动化都会不可靠——错误在运行时才暴露。

### 期望行为

1. 表格中「状态」必须是**单选列**,选项与状态机枚举一一对应:草稿 / 待处理 / 处理中 / 审核中 / 已通过 / 已拒绝 / 失败;
2. `ensure_schema` 启动校验时检查**列类型**(按 field id 取定义,不止按名称):类型不是单选 → 快速失败,错误信息包含列名、当前类型、期望类型与修正指引(飞书不支持直接改列类型,需人工重建列并补选项);
3. (可选)已存在的单选列缺少状态机所需选项时,同样启动报错提示。

### 验收标准

1. 「状态」为文本/多选类型 → worker 启动即报错,信息含修正指引;
2. 类型正确 → 正常启动,行为与现状一致;
3. 全量测试通过(需补充字段类型形态的测试用例)。

## V2-P2 — 支持「JSON 附件上传 → 解析重构 → 反写表格」建行(状态:已记录,机制已明确,细节待定)

### 需求(用户 2026-09-07 描述,已更正旧稿假设)

用户可以不逐项填表,而是把一个材料档案 JSON 作为**附件**上传到多维表格
(上传即创建行)。worker 需要:

1. **识别并下载**附件 JSON(bitable 附件单元格给出 file_token,需经媒体下载取文件内容);
2. **解析并按规定重构**:把 JSON 内容归一成规范档案数据——与 `MaterialProfile`
   的字段与校验规则对齐(品名、喷嘴温度、最大体积流速,可选材料 ID);
3. **反写进多维表格**:把解析出的对应数据写入该行标准列,用户无需逐项填写;
4. 反写完成后,该行走既有「已请求 → 提交 → 审核」流程,不新增旁路。

### 已明确的边界

- 上传入口 = **多维表格附件列**(旧稿假设的"直接写 Git 仓库"已作废);
- 解析/重构/校验规则与阶段 1 `MaterialProfile.validate()` 同源,不允许两套规则漂移;
- 不引入数据库;Git 仓库仍是材料档案唯一真相源——反写只是"填表"的替代手段,提交链路不变。

### 待确认细节(设计时定)

1. **附件列与约定**:固定附件列名;一行多个附件取哪个;附件不是 JSON / 空文件 /
   超大文件如何处理;解析后原附件是否保留;
2. **触发衔接**:上传附件后是否仍须点「提交」按钮才进入处理?候选默认:
   **附件解析反写独立于 已请求**——worker 发现「附件存在且标准数据列为空」即解析反写,
   失败则把错误写入「错误信息」列;数据就绪后仍由用户点按钮提交
   (与现有 Automation 链路一致,不新增自动提交);
3. **JSON 键名约定**:上传 JSON 的字段键用仓库档案同构(英文 `name` /
   `nozzle_temperature` / `max_volumetric_speed`)还是中文列名,或允许两种;
   必填/可选、数值宽容度(如数字字符串),需沉淀一份「用户 JSON 上传约定」;
4. **失败反馈**:解析失败时行状态如何体现(置「失败」还是仅写「错误信息」列),
   修正后重新上传如何重试。

### 验收标准(草案)

1. 行挂合法 JSON 附件 → worker 解析,标准列反写出与 JSON 一致的数据(无需手填);
2. 非法/缺字段 JSON → 不产生脏数据,行上有明确错误提示;修正后重传可收敛;
3. 反写就绪的行点「提交」后,与手填行走完全相同的提交链路(幂等/审核/失败语义一致);
4. 全量测试通过(新增附件下载 / 解析 / 反写的 fake 用例)。

## V2-P3 — PR 被关闭(未合并)时,多维表格显示关闭理由(状态:已记录,待实现)

### 需求(用户 2026-09-07 提出)

Gitea 侧 PR 被关闭(未合并)时,worker 审查同步把行置为 `已拒绝` 的**同时**,
应把「关闭理由」反写进多维表格,让用户直接在表格里看到被拒原因,不必去 Gitea 翻 PR。

### 现状

- 审查同步已处理 closed-unmerged → `已拒绝`(`submission_pr_state` 返回 "closed"),
  但只写状态、不写原因;原因目前只存在于 Gitea 的关闭评论/时间线上。

### 设计要点(细节待定,实现时确认)

1. **理由来源**:关闭 PR 时留下的评论文字。Gitea:issue comments / timeline(closed 事件);
   GitHub:timeline 事件。API 形态按提供方实测确认(参考阶段 1 处理 Gitea
   `commit.id` 差异的前例);
2. **落点**:新增文本列「关闭理由」——与既有文本列一致,由 worker 启动自动创建
   ([fields.py](../src/preset_sync_worker/fields.py) + `ensure_schema` 同步)。
   关闭但无文字说明 → 留空还是兜底文案(如「PR 已关闭,未说明原因」),待定;
3. **边界**:merged 的 PR 不算「被关闭」→ 置 `已通过`,不查理由;
   只有 closed-unmerged 才反写理由;
4. **失败语义**:理由拉取失败不影响状态推进——行仍置 `已拒绝`,理由列留空并打日志
   (行已离开 审核中,下轮不会重试,可人工补录;如需自动补偿则另行设计);
5. **与后续提交的关系**:该行开启新一轮提交时「关闭理由」是保留作历史还是清空,
   与 V2-P0 的「已拒绝后再提交」语义一起定;
6. 实现位置:审查同步逻辑(`submission_pr_state` 附近),与 V2-P0 的改动相邻。

### 验收标准(草案)

1. Gitea 上关闭未合并的 PR 且留了评论 → 该行 `状态=已拒绝`,「关闭理由」= 评论文字;
2. 关闭未留评论 → 状态照常置 `已拒绝`,理由列留空或兜底文案;
3. merged → `已通过`,不写理由;
4. 全量测试通过(新增 closed-PR + 评论的 fake 形态用例)。

## V2-P4 — [全量] 扩展参数集:多维表格全量盘点 → 生成完整 profile 文件(状态:已记录,待细化)

### 背景与目标

阶段 1 的 POC 只用 `品名 / 喷嘴温度 / 最大体积流速` 三个字段生成极简材料档案。本需求目标:做一次**更接近真实生产的全量测试**——多维表格行携带一整套参数,worker 据此生成完整的 profile 文件,验证全链路(实测参数 → 表格 → worker → Git profile)能承载全量字段。

参数分三类(用户 2026-09-07 整理):
- **耗材参数**:要物理实测的线材属性,进入 profile 文件;
- **结构参数**:为命名/继承(PI Code、inherits)、越过切片软件导入关卡(filament_settings_id、version)、未来 validation/troubleshooting 溯源(pm_method_version、submission、generated_at)提供信息,进入 profile 文件;
- **过程记录**:参数调优过程的记录(尤其是照片),**只存表格不进文件**。理由:3D 打印成熟度有限,受设备、耗材状态和操作影响,实验重复性有限——留照片便于日后排查因素,减少无谓的重复实验。

4. C 类照片列:确认 worker 不读取(仅存档);照片的量级与 Bitable 附件上限是否需约定;
5. 全量测试的覆盖范围:单(材料×机型)走通,还是覆盖结构参数矩阵;与 779 文件全量导入(尚未定义)的关系;
6. 与既有表的关系:建议**新表**承载全量列,避免破坏已验收的 POC 表与流程。

### 验收标准(草案)

1. 行填全 A+B 组参数 → 提交 → Git 落盘完整 profile JSON:键与数值与行一致,结构参数正确写入,文件位于 `material/brand/model/slicer/profile` 约定路径;
2. 缺必备参数 → 校验失败且逐字段指明;
3. 照片/过程记录列不参与提交、不影响落盘;
4. 与 V2-P2 协同:附件 JSON 反写全量列(而非 POC 的 3 列);
5. 全量测试通过。
